# 开场策划与用户确认

新一期 `init` 之后、编导稿与分镜稿之前执行。让用户在动手前看见本期怎样混剪：哪些实拍、图片、录屏和用户视频负责哪些内容，如何衔接，何处需要图解、组件、背景、边框和声音，再决定风格与取舍。只改 skill、只写稿或只讨论的任务不启动本阶段；接续旧项目不补历史策划案，用户要求重新定风格时按本流程重新出案。

本阶段的状态、指纹和事件记录规则见 [可恢复状态与流程留痕](workflow-state.md)。`PROJECT.json` 是唯一状态真源；确认后的方案若被直接改动，旧确认自动失效，不能靠改时间戳或手填“已确认”绕过。

## 顺序与停止点

1. 读本期 SRT、配音、design 与用户已有要求，先看清要讲什么、给谁看；盘点 Pexels 等有来源的图片/视频、用户录屏、用户提供视频，以及需按本 skill 交接要求由用户制作并回传的视频。默认尽可能混剪，先按旁白段落提出素材组接、用途与缺口，再确定组件需求；已有信息直接读取，不把盘点变成重复问卷。
2. 按下述“点击式开场问答”收集未定偏好，再按 [组件库生产协议](component-library-integration.md) 按讲解目的检索候选；展示真实预览后让用户选择，实际查看后再写进策划案。
3. 写 `planning/PROPOSAL.json`，运行 `python -X utf8 <skill>/scripts/opening_plan.py build "本期项目"` 生成 `planning/PLAN.md` 与候选项截图/试听文件。
4. 把 `PLAN.md` 和需要用户拍板的问题一起交给用户，**停在这里**。此时不写 `planning/DIRECTING.md`、不建 `EDIT.json` 镜头、不启动 HyperFrames 制作、不派制作任务包。
5. 用户逐项回复后：改了选择就更新 `PROPOSAL.json` 并重新 `build`。展示完整方案并取得明确的整体确认后，再跑 `opening_plan.py confirm --by-user "<用户原话或实际提交的确认选项>"` 记录确认；逐项选择本身不触发此命令。
6. 确认之后才展开编导稿与分镜稿，进入 [三角色协作](team-workflow.md) 的制作流程。

用户没有回复、只回“看到了”“知道了”、或者只确认了一部分，都不算确认。已确认项之外的问题保持待定，不替用户默认。

本阶段可在普通模式用原生问答工具完成，不依赖 `/plan`。Skill 不能自行切换客户端模式；若用户已进入只读 Plan 模式，遵守该模式的写入限制，先在对话内讨论和展示方案，允许写入后再落盘与记录确认，不绕过限制执行初始化或生成命令。已有明确确认仍有效且方案未变时，不重复询问。

## 点击式开场问答

新项目默认使用当前客户端提供的选项框。这里只配置助手如何提问，不安装界面插件或自动切换 Plan 模式；只讨论或修改 skill 时不弹出真实项目启动问卷。

### 固定选择顺序

完成素材盘点后，按以下顺序逐步推进；先等待当前选择，再准备依赖它的候选，不把后面几步一次性弹出。每步先展示参考或真实候选，再给选项。已明确的项直接沿用并告知；不需要的项记录“不使用”后跳过，不强迫用户选装饰。用户可以指定不同顺序。

1. **整体风格**：确定混剪节奏、色板、字体和字幕方向。参考画面应能体现实拍、录屏与图解如何共存；组件库风格用于辅助图形与包装，不要求实拍和录屏改造成插画风。
2. **背景**：选择具体背景及适用范围，例如只用于图解和有留白的录屏镜头。全屏照片、实拍视频和生成视频可以直接作为画面主体，不要求底下的库背景可见；允许不使用额外背景。
3. **装饰边框**：选择是否使用、具体款式与适用镜头。区分软件自身窗口边界与额外装饰框；分别说明实拍、录屏、图解的处理，不默认整片统一套框。
4. **素材组接与辅助组件**：先展示本期代表性实拍图片/视频、已有录屏和用户视频的截图或预览，说明段落中的观看顺序、各自内容作用和交接关系，再推荐必要的图解、对比、标注、标题等组件并展示组合预览。连续采用完整组件场景需说明为什么该段更适合图解；素材缺口对应检索、补录或生成交接任务。未回传视频只展示参考与制作需求，标记待回传；不把生成计划当成已有素材。此处只定分段方案，不提前写逐镜编导稿或生产工程。
5. **动画与转场**：按 [整片动态多样性](motion-variety.md) 确定可轮换的图解动作、图片运动、素材间切换和标注候选池，展示真实预览和避免重复的规则，不把某个默认动效套满全片。为真实操作保留必要观看时间；静态图片推近不替代已约定的待生成视频。
6. **音乐与音效**：先选是否需要，再分别试听具体候选；音乐与动作音分开决定，说明在人声下的使用方式。
7. **整体确认**：展示完整分段方案、组合预览、声音选择与缺口清单，收到“确认方案，开始编导和制作”或同等授权后，才写编导稿、分镜并进入 HyperFrames。

用户中途改选时，只重新核对受影响的后续项：例如换风格需核对背景、外框和组件搭配，关闭 BGM 不重问视觉选择。保持不受影响的答案；完整方案变化后仍须取得与当前版本对应的确认。

- **工具选择**：优先使用当前实际可用的 `functions.request_user_input_async`，普通模式也可用。若只有 `request_user_input`，仅在当前模式及工具规则允许对应问题时调用；不把偏好问题伪装成审批，也不把确认问题交给禁止收集确认的工具。都不可用时退回简短文字问答，说明当前客户端未提供可点击选项。
- **先问方向，再选实物**：从材料读取已知主题、受众、比例和要求，只问会影响方案的缺口。通常每轮 1–3 个问题，每题 2–3 个简短选项，推荐项放首位并标“推荐”；允许用户自由输入，不添加工具已经提供的“其他”选项。不要一次列出整个组件库。
- **方向示例**：整体风格可选“沿用现有组件库 / 更简洁 / 参考我指定的风格”；背景可选“库内动态背景 / 静态背景 / 纯色”；装饰边框可选“按镜头类型使用 / 全部不加 / 统一加”；分别询问 BGM 与动作音的取舍，允许“不用音乐”和“不用音效”。这些是方向，不是虚构的库条目；具体候选必须查过真实目录。
- **先展示，再点选**：组件、背景、边框候选先在对话中用 A/B/C 对照展示真实截图与可打开链接，音乐和音效展示可试听文件及来源。随后选项框沿用相同编号和名称，让选择能对应到具体 ID 或文件。选项框本身是文字交互，不假称支持卡片内图片或音频；缺少预览时按下文降级规则说明。对重复镜头可确认一套组合，例外单独说明。
- **记录与等待**：将实际提交的回答写入 `PROPOSAL.json.questions[].answer`，并更新对应风格及素材字段。异步问答返回“已发起”不等于用户已作答；预选项、超时或沉默都不是选择。等待期间可读取材料、检索候选和准备预览，不能猜测必选答案或启动制作；接续时只问仍未回答的项。
- **最后确认**：答案齐全后 `build` 并展示完整 `PLAN.md`，明确这次确认覆盖当前方案中的组件、背景、边框和声音。工具允许时提供“确认方案，开始编导和制作 / 调整方案 / 暂不制作”三个选项；用户实际提交第一项才记录 `confirm --by-user`。若工具禁止用于确认，则用一句普通文字请求整体确认。选择调整就更新后再展示；选择暂不制作就保持未解锁。此确认不包含导出、公开发布或未授权付费调用。

用户已经针对展示的完整方案明确说“按这个开始”等同等授权时，直接记录，不再要求额外点击。用户说“你推荐一套”仅授权推荐；明确说“不用问我，你定并开始”时按其授权范围处理，不强制走问卷。

## 策划案必须写清楚

`PROPOSAL.json` 是机器记录，`PLAN.md` 是给用户看的版本。两者都覆盖：

- **讲什么**：本期主旨、受众、开头承诺、结尾带走什么，按段落（hook/正文/结尾）列出，不要求逐镜。
- **整体视觉**：色板、默认外框、默认背景、字号与字幕策略；能引用库预设（如 `reference`）就引用，并说明理由。
- **逐段画面方案**：先写每段的素材组接及画面职责（有来源的实拍图片/视频、用户录屏、用户提供或待制作视频、必要图解），再写辅助组件、动画、背景、边框与音效；不使用的项明确写无。在 `visual_plan` 中用文字说明素材顺序、各自增加的信息和连接理由，连续纯组件段落补充内容依据；不要求每段用齐来源或达到固定切镜数。列出可核对的素材路径或来源链接、缺口及检索/补录/生成安排，不用缺素材为由默认改成整段组件动画。沿用 `structure[]` 的 `visual_source`、`visual_plan`、`material_ref`、`material_status` 字符串字段，由 `build` 展示；实际文件与许可仍沿用 `ASSETS.json`，录屏沿用 `RECORDINGS.json`，不另造台账。
- **声音**：需要哪些音效及落点意图、BGM 方向与候选来源。
- **动态多样性**：`variation` 写本期 seed、轮换规则、已展示的候选 item ID 范围和例外；见 [动态多样性](motion-variety.md)。用户明确的具体选择锁定，候选池内按规则分配不逐镜重问；池外变化仍遵守完整方案确认。
- **缺口**：本期待生成的 AI 视频、待录制屏、待找素材、待配音乐，各自由谁产出、当前停在哪一步。
- **需要用户拍板的问题**：每条给出推荐默认值，用户可以直接说“都按默认”。问题回答完才允许记录确认。

策划案是分段级方案，不是逐镜分镜。它承诺的是风格、组件与声音取舍，不承诺具体秒数和每一镜的构图。

## 让用户真的看得见

每一项都要有可查看的证据，不能只有名字：

- **组件与效果**：用库里已有快照 `snapshots/<组件ID>.png`、`snapshots/effects/<效果ID>.png`；缺失时在组件库目录运行 `npm run snapshot --only=<ID>` 生成，需要本机 Chrome。
- **边框与背景**：库没有单件快照，给出画廊深链 `http://127.0.0.1:3031/catalog.html?component=<代表组件>&frame-style=<外框ID>&background-style=<背景ID>`，或按该链接截图后放进项目；用户样板可用 `?scene=reference-stage`，整套预设可用 `?appearance=<预设ID>`。
- **音效**：库内 `assets/sfx/<ID>.wav`，用户可直接试听。
- **音乐**：经 `media-use` 解析出的本地候选文件，登记来源与许可状态。
- **混剪主素材**：Pexels 图片保留具体素材页、作者和许可来源；已有录屏和用户视频展示实际截图或片段并关联原文件。段落中的 `material_ref` 可写可打开的 Markdown 链接，`visual_plan` 可引用真实预览；不将图片或视频伪装成声音候选。尚未取得的素材标明检索中、待录或待回传。

`build` 会把用到的预览复制到 `planning/proposal/previews/`，并在 `PLAN.md` 里用绝对路径嵌入图片和音频，用户在 Codex 里直接能看能听；同时保留画廊链接供实际播放。没有截图或没试听过的项要在文中标明，不能写“已确认”。

画廊是参考工具，不是渲染依赖：成片不引用 3031 服务、浏览器缓存或库的绝对路径。

## 用户改动怎么处理

用户改选、加镜头类型或换风格时，直接改 `PROPOSAL.json` 对应项，重新 `build`，再次交给用户看。改变已确认项后旧确认失效，需要重新确认；不把新选择写成“用户已经同意过”。

确认记录只写用户实际说过的话或可核对的消息摘要，包含时间与范围。后续用户又改了主意，更新提案并重新确认，不覆盖历史。

## 与制作和审片的衔接

- 确认后的选择写进本期 design 与 `DIRECTING.md`；逐镜落地时按 [组件库生产协议](component-library-integration.md) 写进 `EDIT.component_bindings`，不自行替换已确认的组件、背景、边框、音效或音乐。
- 制作中发现确认项不可行（组件不支持该效果、素材许可不适用、库里没有对应能力）时，先向用户说明并给出替代项，再更新策划案，不用“实现不了”悄悄换成别的。
- 独立审片者按 [审片角色](roles/reviewer.md) 对照已确认策划案核对成片；成片与确认项不符且没有用户后续改动记录的，按 major 记录。

## 命令

```powershell
python -X utf8 skills/science-video-director/scripts/opening_plan.py build "本期项目绝对路径"
python -X utf8 skills/science-video-director/scripts/opening_plan.py confirm "本期项目绝对路径" --by-user "用户原话或消息摘要"
python -X utf8 skills/science-video-director/scripts/opening_plan.py check "本期项目绝对路径"
```

`build` 默认不覆盖不是它生成的手写 `PLAN.md`，确认要覆盖时加 `--force`。`confirm` 在没有 `--by-user`、或还有问题没回答时拒绝执行。`check` 被 `episode.py check --phase ready|review|delivery` 调用：新项目未取得开场确认就不能进入制作阶段；旧项目没有登记该契约时不追加错误。

## 降级

- 预览服务没启动、也截不了图时，至少给出画廊深链与组件自带 `previews/<ID>.html` 路径，并明确标注“未截图”，不假装用户看过画面。
- 用户明确说“不用问我，你定”时，记录其原话与范围，按推荐默认值确认，并披露没有逐项确认；这仍然要留确认记录，不能口头带过。
